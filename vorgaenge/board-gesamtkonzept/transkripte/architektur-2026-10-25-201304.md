### Frage 2

**Erstens: nein, nicht systematisch.** Beim Schreiben hatte ich den Code des Board-Plugins, seine Manifeste, die Paketliste des Harness und die READMEs zu Remote-Zugriff, Remotes, Konten und Client-Verbindung. Nicht geladen hatte ich eine Plugin-Bauanleitung oder eine Föderations-Spezifikation — in dieser Installation liegen nur die Pakete mit ihren READMEs. Ich habe den vorhandenen Plugin-Code als Vorlage genommen, nicht die Bauanleitung.

Jetzt nachgesehen: Eine Föderation zwischen zwei Harnessen gibt es nicht. Der Harness ist ein Host mit Browser- und API-Peers; `dsh web --host 0.0.0.0` ist ausdrücklich nicht unterstützt, ACP und SDK laufen über stdio, nicht über das Netz. Die Mehrpersonen-Schicht liegt deshalb im Repository und nicht in einer Harness-Funktion. Das hätte ich beim ersten Mal genauer hinschreiben sollen.

**Zweitens: Ein VPN-Plugin ist in dieser Kiste nicht möglich — und für das Board nicht nötig.** Ich kann den Code für ein solches Plugin schreiben, aber es würde einen vorhandenen VPN-Client bedienen — starten, konfigurieren, seinen Zustand anzeigen. Den Tunnel erzeugen kann es nicht: Ein Plugin kann Prozesse starten und Dateien schreiben, aber keine Netzrechte erlangen. Der Container läuft als normaler Benutzer ohne Capabilities, ohne `/dev/net/tun`, ohne `ip`, `wg` oder `tailscale`. Kernel-WireGuard, Nebula und OpenVPN brauchen genau das.

Der eine Weg ohne TUN ist Tailscale im Userspace-Modus: `tailscaled` arbeitet dann als SOCKS5-/HTTP-Proxy ([Tailscale-Doku](https://tailscale.com/docs/concepts/userspace-networking.md)). Dafür braucht es den Client, einen Tailnet-Schlüssel und einen Kontrollserver — bei Tailscale ein Anbieter, bei Headscale ein eigener Server mit öffentlicher Adresse und offenen Ports ([Headscale](https://headscale.net/stable/setup/requirements/)). Das ist Betrieb, kein Plugin. Und der Gegenpunkt muss erreichbar sein; hinter NAT braucht es einen Vermittler.

Auch direkte Harness-zu-Harness-Kommunikation wird dadurch kein Plugin: Der Harness bietet keinen offenen Netzauftritt, ein Plugin müsste einen eigenen Endpunkt mit eigenem Token bauen, und der Port müsste erreichbar sein. Das ist ein eigenes Projekt. Ohne VPN bliebe WebRTC für direkte Datenkanäle — mit eigenem Vermittler für NAT und eigenem Protokoll; für die Board-Dateien wäre das ein Umbau.

**Was das für die Architektur heißt:** Sie braucht kein VPN. Der gemeinsame Ort ist eine Adresse; wenn du ein privates Netz auf dem Wirt aufsetzt, kann der Git-Ort bei dir liegen statt bei GitHub — das Board bleibt dasselbe. Ich habe beides in [architektur.md](projekte/board/vorgaenge/board-gesamtkonzept/architektur.md) nachgetragen: die Möglichkeit im Abschnitt „Der Ort ist eine Adresse“, den VPN-Plugin-Weg unter „Verworfene Wege“. Die Bedingung „eigener Harness“ ist als bestätigt vermerkt.

Ein privates Netz auf dem Wirt ist eine Systemänderung; die lege ich dir vor, bevor etwas installiert wird — nicht nebenbei.
